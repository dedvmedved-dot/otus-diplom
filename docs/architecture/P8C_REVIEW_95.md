## Критерий одного run: текущий §5 отклонён

Допустимый порядок: dispatch → ответ с ID → test завершён → preflight получил старый секрет → PUT владельца. Все зависимости workflow соблюдены. Продолжительность test ничего не гарантирует. Корректный ID не устраняет эту гонку.

Приемлемый протокол: выделенный owner-controlled runner/label для допуска, без других подходящих runners на всех уровнях. До dispatch владелец закрывает выдачу для этого label и подтверждает отсутствие активных/конкурирующих release runs. После 201 формирует gate для возвращённого ID/attempt=1. Только после подтверждённого PUT (201/204, `routers/api/v1/repo/action.go:124–142`) открывает выдачу. Не заменять и не удалять gate до завершения release: у него свой снимок (workflow:291). Если эксклюзивность, запись или срок не подтверждены — не открывать выдачу, отменить run; не использовать rerun. Эквивалентный явный барьер допустим после ревью. На данном инстансе такой контроль пока не подтверждён.

## Решения по исправлениям и условия публикации

1. **A1 принят.** В preflight и release получить workflow по фиксированным repo/path в дереве точного dispatch commit, отдельно от checkout source/tools. Проверить тип объекта `blob`; отсутствие или mismatch — отказ до побочных эффектов. Сверять независимо наблюдаемый blob с OWNER_GATE и POLICY; использовать тот же проверенный blob в provenance/evidence/final gate (строки 237, 420, 442, 458). Ни mutable `workflow_ref`, ни значение из самого секрета не являются наблюдением.
2. **B заменён.** Включить `enable-openid-connect: true` только на release. Серверный parser — runner/v12 v12.10.2 (`go.mod:14`, `act/jobparser/jobparser.go:317–329`); `services/actions/task.go:162–187`, `auth.go:92–101`: `permissions.id-token` не выдаёт credentials. Для Actions issuer — `https://git.aiopslab.online/api/actions` (`routers/api/actions/id_token.go:137–144` и discovery `/api/actions/.well-known/openid-configuration`). Dispatch `sub` (`services/actions/auth.go:148–155`) не доказывает SAN сертификата. Нужны подтверждение доверия CA к issuer и audience, точный SAN и привязка к одобренному workflow, согласованные trust roots для sign/verify/verify-attestation. Не расширять regexp и не подставлять `sub` наугад. Без доказательства оставить B закрытым.
3. На строках 82/392 формируется тег `vv3.1.3`: исправить URL, сохранить SHA-256 проверку. Проверять обе аттестации для того же digest (422–427), согласовать проверки аннотаций с политикой.
4. Engineer готовит PR и автономные положительные/отрицательные тесты (неверный blob, неверный issuer/identity, задержка PUT и чужой run). После повторного review — публикация изменённого workflow, фиксация merge commit и нового blob из опубликованного дерева; владелец обновляет policy pin и подтверждает барьер и доверие OIDC. Только затем отдельное решение о первом B. Это ревью не разрешает dispatch, выпуск, смену секретов или lock.
