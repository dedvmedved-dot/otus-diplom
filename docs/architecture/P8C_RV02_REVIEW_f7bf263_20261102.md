## RR-01 — завершить ingress-дизайн (OD-03)
В R1 §4 одновременно написано «B3 решён» и «Внешний listener→dataplane НЕ моделируется
… требует будущего design-решение» (строка99). Выбранной exposure/source-address модели
и конкретной границы ingress нет. PLANNED generated-runtime допустим, но не заменяет дизайн.

Архитектор дополнительно проверил официальный Envoy Gateway v1.9.1:
commit 0260554fd4f33b787aad77a129fc0ffeb00c1f29.
- internal/gatewayapi/translator.go: minEphemeralPort=1024, wellKnownPortShift=10000.
- internal/gatewayapi/listener.go, blob 3d8376553ad570ab22476a7d163053eaf32d3883:
  servicePortToContainerPort в обычном managed Kubernetes режиме переводит privileged
  port в port+10000; Host/remote/NeedToSwitchPorts=false — исключения.
- internal/infrastructure/kubernetes/proxy/resource_provider.go,
  blob 3ce6421fae1b4c521190cb48feca11a4d9172bcd: Service.port=ServicePort,
  Service.targetPort=ContainerPort; возможные provider patches следует учитывать.
Следовательно, для режима по умолчанию кандидат HTTPS443→10443 выводится из source.
Это не live-наблюдение. Нельзя оставлять определяемый source default полностью UNKNOWN,
или выдавать произвольный test fixture за реальную генерацию нашего Gateway.

Завершить одну выбранную модель: Service type/externalTrafficPolicy, MetalLB exposure,
кто допускается к listener, где действует ingress enforcement, какой source address
сохраняется/переписывается, targetPort, ownership selectors. Проверить соответствующие
defaults/overrides по этой версии и существующим repo values. Не угадывать runtime LB IP,
UID и healthCheckNodePort: для них задать точные будущие field checks.

Явно выбрать и обосновать candidate ingress boundary: ограничивающая dataplane policy
или обоснованная граница на другом уровне. Egress-only сам по себе ingress не ограничивает.
Решение не является одобрением YAML/apply; если требуется новое ограничение, записать delta.
Не вводить namespace-wide deny в envoy-gateway-system.
Различить kubelet probes, LB health checks и отсутствующий active backend health-check;
для каждого необходимого потока указать source/destination/port и правило либо исключение.
Закрытие RR-01: нет «будущее design-решение»; есть законченный кандидат и только измеримые
generated-runtime проверки для execute-gate.

## RR-02 — реальные условия S0–S4 и проверяемый rollback (OD-04)
1. S0 сейчас: «Pod не ограничены (F-NP пусто на срезе)». F-NP — только Calico NetworkPolicy,
   не networking.k8s.io NetworkPolicy и не весь policy union. Заменить на условный baseline:
   ожидаемая исходная конфигурация + точный будущий freshness precheck; отличие → STOP.
   Не выдавать исторический срез за current отсутствие ограничений.
2. Разделить S2 на последовательность операций. baseline-allow-dns-egress тоже изолирует
   выбранные Pods по egress. Снятие baseline-default-deny ещё не снимает эту изоляцию.
   Для каждой операции явно показать union/сохраняемые allowances; вернуть исходное состояние
   только после корректного удаления всех новых selecting policies с UID preconditions.
3. S3 «удалить flows + workloads» — неопределённый порядок и расширение NetPol rollback
   на workload deletion. Если требуется остановка созданных Portal/Job/Gateway, указать
   отдельную зависимость deployment gate и безопасный порядок; не считать разрешённым удаление
   workloads из текущего NetPol/doc gate. Существующие CNPG/controller workloads не трогать.
   Также определить безопасную границу внешнего трафика при rollback S4.
4. §5 оставляет только перечень слов «command/field/time-window/timeout/STOP/rollback».
   Нужна заполненная таблица каждого pre/post check: точный объект/API/поле или ограниченная
   команда, ожидаемый результат, максимальное окно ожидания, свежесть, исход при недоступности,
   какая стадия откатывается. Отдельно состояние CNPG, API/DNS, WAL/S3, operator reconciliation
   и будущих Portal/Gateway. Не заменять живую успешность старым LastBackupSucceeded=True.
   Наблюдать естественный прогресс; idle/no progress не превращать ни в PASS, ни автоматически
   в отказ. Указать как неопределённый результат блокирует дальнейший rollout.
   Backup/restore/PITR/failover или destructive probes повторно не запускать.
Закрытие RR-02: проверяемы начальное состояние, каждый промежуточный union, UID-safe rollback
и реальные критерии прохождения. Это только проект, не разрешение выполнить операции.

- В §6 строка129 неверно называет namespace label k8s.io/metadata.name.
  Точный ключ: kubernetes.io/metadata.name, как в кандидатном YAML и K8s 1.36 docs.
  Полный ключ owning-gateway-namespace также gateway.envoyproxy.io/owning-gateway-namespace.
- В строках всё ещё отсутствуют явные namespace или определения shorthand; R1/R3/P7 без
  файла/commit/time не равны заявленной полной трассируемости. Допускается компактный словарь
  источников и selectors, но каждый из 14 FLOW-ID должен ссылаться на однозначную запись.
  Полные blob/SHA могут находиться в словаре, не обязательно повторяться 14 раз.
  Для PLANNED указать source-manifest, а не придумывать runtime record/time.
- Не утверждать «нет controller→DB/S3» как доказанное отсутствие любого такого трафика;
  корректно: необходимость такого permission не установлена, в дизайн не включается.
- PR-3 «kubectl get endpoints/default/kubernetes» — не корректный namespace-qualified argv.
  Сверка адресов не подтверждает active enforcement. Использовать точный namespace/name/GVR;
  если EndpointSlice выбран, задать service-name selector/проекцию/completeness. Это предложение,
  а не новый сбор. Не держать формулировку «правило не блокирует rollout» при открытых проверках.
- PR-4 обещает freshness «не новый DNS-проб», но не содержит действия. Старое P7 evidence
  нельзя перечитать и получить новую freshness. Либо требуемое свежее наблюдение явно предложено
  с source/resolver/qname/type/timeout/attempts/allowlisted output/errors/лимитом, либо честно
  remains stale с решением STOP в будущем gate. Указать границы пути node versus Pod.
- Заголовки PLAN/flow-matrix сейчас выдают авторский RESOLVED за Current Architect decision.
  Разделить AUTHOR_PROPOSAL и ARCHITECT_ACCEPTED; синхронизировать также gaps.md.
