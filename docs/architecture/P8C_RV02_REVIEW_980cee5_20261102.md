## MI-01 — доказанная несовместимость типизированного списка

project_pod_identity начинается с _require(obj, 'Pod', 'v1'). В standalone-контексте
это строгая проверка. Но F-I1 передаёт ему items типизированного core/v1 PodList напрямую:
внутри такого списка TypeMeta каждого Pod может отсутствовать.

Официальные исходники Kubernetes v1.36.2 проверены через Connector:
- staging/src/k8s.io/api/core/v1/types.go, blob ac0494f3c51472a39ab380f99e09882cfd05773c:
  PodList.Items имеет тип []Pod.
- staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/types.go,
  blob c8b87f20c8e1869a1163b711c32180412f63ed7d:
  TypeMeta.Kind/APIVersion optional и json omitempty.
- staging/src/k8s.io/apimachinery/pkg/runtime/serializer/json/json.go,
  blob 24f66a10174b04d6fcdde30d5155b829ae63daec: обычная сериализация JSON.
- staging/src/k8s.io/apimachinery/pkg/runtime/serializer/json/collections.go,
  blob 075163ddd81e3d12dff33098d70ff7d31780a9d4:
  encodeItemsObjectSlice → encodeValue → json.Marshal(item), без добавления TypeMeta.
- collections_test.go того же каталога, blob 0defd9e6b6dd0c037dc57be5b757d3199a1bc6a1:
  тесты typed CarpList сохраняют элементы без kind/apiVersion.

Fixture derived-i1-fixture.json честно говорит, что wrappers kind/apiVersion синтетические.
Прежний тест проверял восстановленную проекцию, а не реальный wire-format PodList.
Reviewer удалил только эти синтетические поля: три допустимых варианта дают ITEM.
Четвёртый сбой — valid-but-unbound digest при отсутствующем TypeMeta ошибочно классифицируется
как PARSE_ERROR вместо UNSUPPORTED. Контроли explicit metadata и 10 некорректных значений проходят.
Всего supplied regression: 6 методов, 2 PASS / 4 FAIL на точном принятом source.
Review-only адаптер в памяти даёт 6/6 PASS; исходники не изменены, live не выполнялся.

Это ДОКАЗАННЫЙ source-дефект и объяснение, совместимое с наблюдаемым ITEM.
Точное поле live-отказа всё ещё UNKNOWN: raw response не сохранён.
Не писать «отсутствие kind доказано live» и не утверждать, что иных причин ITEM быть не может.
