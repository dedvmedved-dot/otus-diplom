## Блокирующие расхождения и условия повторной приёмки

1. **Допуск до первого действия.** `release_gate` необязателен и лишь сохраняется: ни один шаг не проверяет его перед сборкой и push. До доступа к credentials и любых release-действий требуется проверка допуска владельца, source/workflow SHA, repo/package, ref, срока и бюджета попытки. Проверить офлайн отказы для отсутствующего/просроченного/чужого допуска.
2. **Развести source и инструменты.** Все jobs извлекают source, в котором нет `test_forgejo_lock_gate.py` и `forgejo_lock_gate.py`. Указать отдельный неизменяемый pin инструментов и независимые каталоги. Проверять наличие всех используемых файлов по соответствующим деревьям, не подменяя source новым HEAD.
3. **Проверять нужный registry.** `release-check.py:211–219` использует фиксированный GHCR/repository и читает GitHub credentials, а шаблон передаёт другую пару для registry владельца. Нельзя передавать эти credentials старому helper. Связать назначение push, разрешённый адрес аутентификации, manifest bytes/header, image и запись lock; неизвестное назначение — отказ до сетевого запроса. Офлайн-тест с mock transport.
4. **Проверять подписанное утверждение того же запуска.** `release-check.py:54–58` строит GitHub predicate без subject. `update-lock` читает именно локальный `provenance.json`, а не результат `verify-attestation`. Digest из `GITHUB_ENV` и файлы `RUNNER_TEMP` не передаются между jobs через `needs`. Передать доказательства явно либо проверять в одном job. Брать subject из проверенного in-toto statement, builder/source из predicate, сверять issuer/identity, тип, image/digest, source и конкретный workflow SHA/run. Discovery само по себе не доказывает доверие подписанту. Тесты на реальной форме данных: отсутствие проверенного результата, другой run/registry, несвязанный subject и подмена predicate исключают запись; положительная проверка — только на временной копии.

Для доработки использовать `portal/versions.lock:image` как предполагаемое основное место, с проверкой registry и digest как одной пары. Не добавлять вторую независимую запись в `images.lock` и не менять lock до отдельного решения владельца. P0 и SHA action, доверие OIDC, бюджет dispatch и публикация остаются отдельными предпосылками. Только офлайн-доработка и повторное ревью. Digest/provenance — NOT_VERIFIED; runtime §6 — NO-GO, #32 — HOLD, P8D не открыт. Независимая ревизия CA/UID и подтверждение pull не заменяются этим решением.
